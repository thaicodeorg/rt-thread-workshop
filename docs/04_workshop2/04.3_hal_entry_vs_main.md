# `hal_entry.c` vs `main.c`: โปรเจกต์แบบไหนใช้อันไหน

<span class="md-tag">Foundation</span> <span class="md-tag">Project Structure</span>

## สิ่งที่คุณจะเข้าใจหลังอ่านหน้านี้

- [ ] ทำไมโปรเจกต์บางตัวไม่มี `applications/main.c`
- [ ] 2 รูปแบบโปรเจกต์บน RT-Thread Studio
- [ ] เมื่อไหร่เขียนโค้ดที่ `hal_entry.c` เมื่อไหร่เขียนที่ `main.c`
- [ ] โค้ดตัวอย่างจาก Workshop ใช้รูปแบบไหน

---

## ปัญหา: เปิดโปรเจกต์แล้วไม่เจอ `applications/main.c`

คุณสร้างโปรเจกต์ `Hello-World` บน RT-Thread Studio แล้วเห็นแบบนี้:

```text
Hello-World/
├── src/
│   └── hal_entry.c          ← มีแค่นี้!
├── libraries/
├── rt-thread/
└── ...

❌ ไม่มีโฟลเดอร์ applications/
❌ ไม่มีไฟล์ main.c
```

**ทำไมล่ะ?** คำตอบคือ: โปรเจกต์นี้ใช้ **รูปแบบ FSP Native** ไม่ใช่รูปแบบมาตรฐาน RT-Thread

---

## 2 รูปแบบโปรเจกต์

### รูปแบบที่ 1: FSP Native (`hal_entry.c` เบ็ดเสร็จ)

ใช้กับบอร์ด Renesas RA โดยเฉพาะ โครงสร้างอิงตาม **Renesas FSP**

```text
โปรเจกต์/
├── src/
│   └── hal_entry.c          ← เขียนโค้ดที่นี่
├── libraries/               ← FSP ทั้งหมด
└── ...
```

**ลักษณะ:**
- ไม่มี `applications/`
- ไม่มี `main.c`
- โค้ดทั้งหมดเขียนใน `hal_entry()`
- วิ่งเข้า `hal_entry()` ตอนบูตเสร็จ → วนลูป `while(1)` ในนั้นเลย

**ตัวอย่างโค้ด (แบบที่คุณเห็นใน Workshop):**

```c
#include <rtthread.h>
#include <rtdevice.h>
#include "hal_data.h"

#define LED_PIN    BSP_IO_PORT_01_PIN_02
#define IRQ_TEST_PIN "p907"

void irq_callback_test(void *args) {
    rt_kprintf("\n IRQ10 triggered \n");
}

void hal_entry(void)
{
    rt_kprintf("\nHello RT-Thread!\n");
    
    // ตั้งค่า Interrupt
    rt_uint32_t pin = rt_pin_get(IRQ_TEST_PIN);
    rt_pin_attach_irq(pin, PIN_IRQ_MODE_FALLING, irq_callback_test, RT_NULL);
    rt_pin_irq_enable(pin, PIN_IRQ_ENABLE);

    // ลูปหลัก → กระพริบ LED
    while (1) {
        rt_pin_write(LED_PIN, PIN_HIGH);
        rt_thread_mdelay(500);
        rt_pin_write(LED_PIN, PIN_LOW);
        rt_thread_mdelay(500);
    }
}
```

**ข้อดี:**
- ง่าย ไม่ต้องคิดเรื่อง Thread
- ไฟล์เดียวจบ
- คล้าย Bare-metal แต่มี RTOS API ใช้

**ข้อเสีย:**
- `hal_entry()` ไม่ใช่ Thread มาตรฐานของ RT-Thread
- ถ้าทำงานหนักใน `hal_entry()` จะบล็อกระบบบางอย่าง

---

### รูปแบบที่ 2: มาตรฐาน RT-Thread (`hal_entry.c` สะพาน → `main.c`)

โครงสร้างมาตรฐานที่ใช้กับบอร์ดทุกยี่ห้อ (STM32, Nuvoton, etc.)

```text
โปรเจกต์/
├── applications/
│   └── main.c               ← เขียนโค้ดที่นี่
├── board/
│   └── board.c              ← rt_hw_board_init()
├── src/
│   └── hal_entry.c          ← แค่เรียก rtthread_startup()
├── libraries/
└── ...
```

**ลักษณะ:**
- มี `applications/main.c`
- `hal_entry.c` สั้นมาก — แค่เรียก `rtthread_startup()`
- RT-Thread Kernel สร้าง Main Thread → วิ่งมา `main()`

**ตัวอย่าง `src/hal_entry.c` (รูปแบบนี้):**

```c
void hal_entry(void)
{
    rtthread_startup();  // ← แค่นี้! แล้วเขียนโค้ดใน applications/main.c
}
```

**ตัวอย่าง `applications/main.c`:**

```c
#include <rtthread.h>

int main(void)
{
    while (1) {
        rt_kprintf("Hello from Main Thread!\n");
        rt_thread_mdelay(1000);
    }
    return 0;
}
```

**ข้อดี:**
- `main()` เป็น Thread มาตรฐาน มี Scheduler ดูแล
- สร้าง Thread เพิ่มได้สบาย
- ใช้ Software Packages ได้เต็มที่

**ข้อเสีย:**
- ไฟล์กระจัดกระจายหลายที่
- ต้องเข้าใจ Thread concept

## เปรียบเทียบตรง ๆ

| คุณสมบัติ | รูปแบบ 1: FSP Native | รูปแบบที่ 2: RT-Thread Std |
|----------|---------------------|---------------------------|
| มี `applications/`? | ❌ ไม่มี | ✅ มี |
| มี `main.c`? | ❌ ไม่มี | ✅ มี |
| เขียนโค้ดที่ไหน? | `src/hal_entry.c` | `applications/main.c` |
| `hal_entry()` ทำอะไร? | มีโค้ดเต็มไปหมด | แค่เรียก `rtthread_startup()` |
| `main()` เป็น Thread? | ไม่มี `main()` | ✅ ใช่ |
| Scheduler ดูแล `main()`? | ❌ ไม่ใช่ | ✅ ใช่ |
| ใช้ Packages ได้สะดวก? | ⚠️ ได้ แต่ไม่เต็มที่ | ✅ ดีมาก |
| เหมาะกับ | ง่าย ๆ / ฝึกเริ่มต้น | โปรเจกต์จริง / IoT / AI |
| บอร์ดที่พบ | Renesas RA บางเทมเพลต | STM32, Nuvoton, ทั่วไป |

## เมื่อไหร่ใช้แบบไหน?

### ใช้ `hal_entry.c` (รูปแบบ 1) เมื่อ:
- โปรเจกต์เล็ก ๆ — แค่กระพริบ LED อ่านเซ็นเซอร์
- ยังไม่ต้องการ multi-threading จริงจัง
- ต้องการไฟล์เดียวจบ
- Workshop 1-4 ของคอร์สนี้ใช้แบบนี้

### ใช้ `main.c` (รูปแบบ 2) เมื่อ:
- ต้องการสร้างหลาย Thread (อ่านเซ็นเซอร์ + ส่ง WiFi + อัปเดตจอ พร้อมกัน)
- ใช้ Software Packages มาก ๆ
- โปรเจกต์ IoT / AI จริงจัง
- Workshop 5-9 แนะนำให้ใช้แบบนี้

## จะรู้ได้ยังไงว่าโปรเจกต์เราเป็นแบบไหน?

### วิธีที่ 1: ดู Project Explorer

```text
ถ้าเห็น applications/  → รูปแบบที่ 2 (มี main.c)
ถ้าไม่เห็น              → รูปแบบที่ 1 (ใช้ hal_entry.c)
```

### วิธีที่ 2: ดูเนื้อหา `src/hal_entry.c`

```c
// ถ้าเปิดมาแล้วมี while(1) ยาว ๆ → รูปแบบที่ 1
// ถ้าเปิดมาแล้วมีแค่ rtthread_startup(); → รูปแบบที่ 2
```

### วิธีที่ 3: ดู Template ตอนสร้างโปรเจกต์

| Template ที่เลือก | รูปแบบที่ได้ |
|------------------|------------|
| `vision_board_blink_led` | รูปแบบที่ 1 (`hal_entry.c`) |
| `vision_board_wifi` | รูปแบบที่ 2 (`main.c`) |
| STM32 ทั่วไป | รูปแบบที่ 2 (`main.c`) |

```text

ถ้ามี applications/main.c    → เขียนโค้ดใน applications/main.c

ไม่ต้องตกใจที่ไม่เหมือนกัน — เป็น 2 รูปแบบที่ถูกต้องทั้งคู่!
```

    **"จะแปลงจากรูปแบบ 1 เป็นรูปแบบ 2 ได้ไหม?"**

    - ได้ แต่บาง Package อาจออกแบบมาสำหรับรูปแบบที่ 2
    - ถ้า Package ต้องการ `main()` thread อาจมีปัญหา

    **"ทำไม Renesas ถึงใช้รูปแบบที่ 1?"**
    - บางเทมเพลตจาก Renesas อิง FSP Native structure
    - ชอบให้ `hal_entry()` เป็นจุดเริ่มต้นแทน `main()`

    **"Workshop 1-4 ใช้รูปแบบไหน?"**

    - Workshop 5 ขึ้นไปแนะนำให้สร้างโปรเจกต์ใหม่ด้วยรูปแบบที่ 2
